# Reranker runtime parity + latency (AITeamVN/Vietnamese_Reranker)

Run window: 2026-10-23 21:59 to 23:34 +07 (UTC+7); report generated by `report.md` (see its header). Files: `candidates.json`
(first-stage top-20 per question, sha256 `d5d8fa6a...3be`), `scores_<label>.json` (raw per-pair scores, per-query wall time),
`tokcheck_*.json`, `report.json` / `report.md` (all tables), `adhoc/` (unarchived-protocol timing experiments, see below),
`failed_attempt1_harness_race/` (logs of a harness race, see below), `run_gguf_sequence.sh` (driver of the GGUF runs).

Caveat first: queries are the benchmark *questions* (not the agent's own tool-call queries); the metrics against gold ids are rank
metrics on article ids only (45 answerable questions per benchmark), NOT answer correctness. Latency was measured on a shared
Mac (other agents were running processes) and on a shared H100 PCIe: diagnostic only, not the reportable latency profile.

## Findings
* The converter output was NOT faithful at first: `convert_hf_to_gguf.py` writes no `add_bos_token` and no pair separator, so
  llama-server fed `query </s> passage </s>` instead of `<s> query </s></s> passage </s>` (logit 1.45 became -3.91 on a short
  pair although the encoder output was identical, cos >= 0.9999998, for the HF token ids). `gguf_fix_pair_template.py` repairs
  the metadata; afterwards the server's prompt-token count equals the HF pair length on 399/400 checked pairs per GGUF (the one
  exception is a pair cut by the client-side token cap: 1023 vs 1024 tokens).
* After the fix the GGUF scores track torch fp32 with max abs difference 0.094 (f16), 0.097 (f32), 0.31 (Q8_0); f16 and f32
  differ only by that ggml GELU/graph difference, not by precision. f16 is the Mac choice; Q8_0 is smaller but visibly less
  faithful (top-3 ordered agreement 0.96 vs 0.99).
* Chunking matters: with prefix truncation, gold evidence that starts beyond the first ~3000 characters is invisible. Gold ranks
  of the 7 HCMUT tasks (005, 006, 007, 015, 034, 037, 047) plus LVN-037 are in `report.md`; e.g. HCMUT-015 rank 7 -> 1,
  HCMUT-037 3 -> 1, HCMUT-005 5 -> 2 (reference fp32).
* Harness race (kept for transparency): the first attempt of the GGUF sequence polled `/v1/models` without failing on HTTP 503
  while the model was loading, so `gguf_f32_chunk` and `gguf_f16_chunk` failed immediately and nothing was written; the logs are in
  `failed_attempt1_harness_race/`; the sequence was fixed (`curl -sf`) and restarted; `gguf_f32_nochunk` from attempt 1 (valid) was kept.
* `adhoc/`: 10 HCMUT queries (tasks 3-12, chunk policy) timed back to back on the f16 GGUF with different server flags
  (p50 ms/query: `-ub 8192` 8293; `-ub 1024` 7338; `-fa on` 8465; `-fa off` 8204; `-np 4` 8853) and torch MPS fp16 batch 1 (9179),
  max abs difference MPS-fp16 vs GGUF-f16 0.069 over 200 pairs. No server flag gave a consistent gain; GGUF was not slower than
  torch/MPS. These timings are noisy (shared machine) and are not reportable.

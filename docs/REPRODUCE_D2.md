# Reproducing the results of the LuatCheck D2 report

Audience: a lecturer, a team member or another agent who has this repository and wants to check or regenerate every result the D2 report (`report_d2/main_d2.tex`) contains. Every command is meant to be copy-pasted from the repository root unless stated. Nothing here relaxes `AGENTS.md`: inference is real, a backend failure is an execution error, nothing is mocked, filled in or estimated.

`report_d2/RESULTS_PROVENANCE.md` (table to run to commit to command) is regenerated by `make report-check` after the final report edit. The version on disk when this was written (18:55 +07, status OK) maps `tab:benchmark-{main,ops,paired,baselines,behaviour,strata}` to the two v3 runs, `tab:benchmark-latency` to `d2-mac-latency-v3sys-v1`, and `tab:trace` to `d2-gpu-main-hcmut-v3`; it does not yet contain the r2 runs or the comparison. Use the regenerated file, not this document, as the authority for table-to-run mapping once the report is final.

Verification tags used below: **[ran]** = executed read-only while writing this document, the outcome is stated; **[read]** = derived from code, manifests and logs, not executed here.

## 0. Ground rules

1. **Never write into a committed run directory.** `evaluation/runs/*` is evidence; it is tracked in git, so a clone already contains every trial, judgment and manifest. Re-collection uses a new run id (suffix `-repro1`) and `--kind diagnostic`, which can never become report evidence. Re-analysis is done in a scratch clone (`git clone <repo> /tmp/d2-scratch`), so `git diff` shows exactly what changed.
2. **Secrets.** The judge needs two environment variables, `LUATCHECK_JUDGE_BASE_URL` (not secret; must equal `base_url` in `config/benchmark/judge_gateway.json`) and `LUATCHECK_JUDGE_API_KEY` (credential). They are read from the process environment or from a git-ignored `.env`. Do not print, log or commit them. No other step needs a credential.
3. **Four levels of reproduction**, in increasing cost. A and B are exact; C and D are statistical (section 5).

| Level | What | Needs | Time |
|---|---|---|---|
| A | audit the stored artifacts: hashes, locks, manifests, independent recomputation of strict success | Python only | minutes |
| B | regenerate analysis, tables, comparison from stored trials and judgments | repo venv | minutes |
| C | re-collect trials with real inference (Mac Metal, or H100) | model servers | GPU 16 to 34 min per run; Mac 56 min |
| D | re-judge with the API judge | gateway access, about USD 1 per run | 40 to 90 min per run |

4. **Which commit to check out.** Levels A and B: the commit of this document (all tools are in it). Level C, v3: `957579b58f8104a0f935d267828166c0247010fc` for an exact match of the original code (harness 1.1.2); current code with the default configuration also yields the v3 system (the Mac latency run was collected that way, harness 1.2.0), guarded by the replay-identity tests of section 3.13. Level C, r2 and Mac: `cdb6b243aac536dcfdec6fe137dc8c08f4b988f1` as run. At the commit of this document the collection code and configuration are unchanged since `cdb6b24` apart from UI-only directories and demo profiles: the `git diff --stat` command of section 4.2 printed nothing [ran]; re-run it before assuming this holds at a later commit.

### 4.3 Recompute strict success from the raw files [ran]

Reads only `trials.jsonl`, `judge/private_mapping.json`, `judge/judgments.jsonl` and `analysis/summary.json`; imports nothing from the repository; implements the semantics of `evaluation/judge_rules.py:judgment_strict_success` (behaviour appropriate, correctness 2, completeness 2, no counted claim other than `supported`; for an abstention output - the task expects a refusal, or the trial ended `refused` or `clarified` - claims labelled `not_established` are ignored; an execution error is a failure and was never judged; a trial without a valid judgment, or with `judgeable: false`, is unknown and counts as a failure). Save as `recompute.py`, run `python -I recompute.py evaluation/runs/<run> ...`.

```python
import json, sys
from collections import defaultdict
from pathlib import Path

def strict(j, abstains):
    counted = [c for c in j["claims"] if not (abstains and c["support"] == "not_established")]
    return bool(j["behaviour_appropriate"] and j["correctness"] == 2 and j["completeness"] == 2
                and all(c["support"] == "supported" for c in counted))

for run in map(Path, sys.argv[1:]):
    key = lambda r: (r["benchmark"], r["variant"], r["seed"], r["task_id"])
    rows = {}
    for line in (run / "trials.jsonl").read_text(encoding="utf-8").splitlines():
        if line.strip():
            r = json.loads(line)
            if key(r) not in rows or r.get("attempt", 1) >= rows[key(r)].get("attempt", 1):
                rows[key(r)] = r                                  # latest attempt wins
    rid = {key(m): m["review_id"] for m in json.loads((run / "judge/private_mapping.json").read_text(encoding="utf-8"))}
    valid = {}
    for line in (run / "judge/judgments.jsonl").read_text(encoding="utf-8").splitlines():
        if line.strip():
            r = json.loads(line)
            if r["status"] == "valid":
                valid[r["review_id"]] = r["judgment"]
    cells = defaultdict(lambda: {"planned": 0, "success": 0, "unknown": 0, "errors": 0})
    for k, r in rows.items():
        c = cells[(k[0], k[1])]; c["planned"] += 1
        j = valid.get(rid.get(k))
        if r["system_error"]:
            c["errors"] += 1
        elif j is None or not j["judgeable"]:
            c["unknown"] += 1
        elif strict(j, r["expected_behavior"] == "refuse" or r["terminal_status"] in ("refused", "clarified")):
            c["success"] += 1
    summary = json.loads((run / "analysis/summary.json").read_text(encoding="utf-8"))["cells"]
    ok = True
    for (b, v), c in sorted(cells.items()):
        s = summary[f"{b}/{v}"]["strict_success"]
        same = (c["success"], c["unknown"]) == (s["successes"], s["unknown"]); ok &= same
        print(f"{run.name:26s} {b:13s} {v:11s} N={c['planned']:3d} strict={c['success']:3d} ({100*c['success']/c['planned']:5.1f}%) "
              f"unknown={c['unknown']:2d} errors={c['errors']}  summary.json: strict={s['successes']} unknown={s['unknown']}  {'OK' if same else 'MISMATCH'}")
    print(run.name, "ALL MATCH" if ok else "MISMATCH")
```

Outcome when run on the six GPU runs: `ALL MATCH` for each, and the percentages equal the table in section 1.2 (for example `d2-gpu-r2-4b-labour-v1 labour_vi_v1 off N=150 strict=93 (62.0%)`). The CI is the percentile bootstrap over tasks (task value = mean over the cell's seeds of the 0/1 success; 5000 resamples of `numpy.random.default_rng(20261023).integers(0, n, size=(B, n))`, 2.5th and 97.5th percentiles, `evaluation/stats.py`). Note that this checks the arithmetic given the judgments, not the judgments.

## 5. What will not reproduce byte for byte, and the expected tolerance

No replicate of any collection cell exists in this repository, so no tolerance below is a measured replicate spread. Where a scale is given it is derived from numbers that are in the artifacts and is labelled as such.

| Source of variation | Effect | What to expect |
|---|---|---|
| LLM judge via API (Level D) | The model revision behind the route is not pinned, routing is not attested, no temperature or seed is sent, and the judge is one model with one judgment per packet. The gateway also appears to return identical completions for byte-identical requests (`docs/BENCHMARKS_AND_METRICS.md` section 4), which is why attempts after the first prefix a disclosed line; a re-judge of an identical packet may therefore return a cached verdict, and is then not an independent judgment. Re-judging can change individual verdicts | Compare strict success per cell against the table in 1.2 and the CI width (about 7 to 10 percentage points per side for 150 trials). Report the number of invalid attempts (19 to 45 % of attempts in the recorded runs, mostly "quote absent from supplied source", "claim quote absent from candidate answer" and HTTP 524) and of packets that stay unknown after all rounds (2 to 11 per run). Unknown trials count as failures, so a worse gateway day lowers the lower bound |
| Controller sampling at temperature 0.7 (Level C) | The seed is sent with every request, but llama.cpp reproduces a seeded sample only for a single request on an idle server (`seed_reproducible`, a 4-request canary, is true in every manifest). The GPU runs used 16 concurrent slots with a unified KV pool, so batch composition varies from run to run; different logits can follow, and a different token anywhere changes the trajectory. This is an expectation from how the runs are executed, not a measured replicate | Trial-level outcomes will differ. Cell-level scale from the artifacts: the seed-to-seed standard deviation of strict success within a cell (50 trials per seed) is 0 to 9 percentage points across the 18 variant cells of the six GPU runs (for example r2-4B labour L1: seeds range 46 to 62 %). The report states that differences under about 10 pp are within noise at 50 tasks. Treat a new run as consistent if each pooled cell lies within the reported bootstrap interval (or within about 10 pp), and the large contrasts keep their sign: r2 above v3 by 9 to 17 pp per cell, r2-4B above r2-2B by 25 to 40 pp, L1 not above OFF in v3, oracle above every system variant (not like-for-like: the oracle is scored on answerable tasks only) |
| Build and hardware | Mac (Metal) and CUDA kernels differ numerically; the GPU reranker is torch fp16 and the Mac reranker a GGUF f16 conversion (max abs score difference 0.126, one top-1 flip in 100 questions, section 1.2). Accuracy is therefore taken from the GPU runs and latency from the Mac run, and the two `l1_rerank` rows are never pooled | A Mac accuracy run is not a replicate of the GPU runs |
| First-stage retrieval ties | Records with identical text are ordered differently on the Mac than on server 82: 3 of 377 searches in the v3 replay (`tests/test_r2_switches.py` allows at most 3). The cause (BLAS, scikit-learn, sort stability) is not established; the GPU manifests do not record scikit-learn or rank-bm25 versions | The replay-identity tests may report up to 3 ties on another machine; more than 3 fails them |
| Latency and memory | Depend on the chip, memory pressure, thermal state and background load; the recorded run had a 1-minute load of 2.97 on 10 CPUs and the sampled `ps` RSS excludes Metal buffers. GPU latency is recorded but never reportable (concurrency, shared GPU) | Same order of magnitude and ordering on an idle M4 16 GiB (OFF < L1 < L1+rerank in trial p50; decode about 94 tokens/s; reranker call 2 to 4 s per search). Another chip or a busy machine gives different numbers; report your own with the machine state. Never compare with the GPU wall times |
| Shared-server contention and request timeouts (GPU) | Only the 4B runs have `wall_timeout` rows (9 and 8). The same tasks recur across variants and seeds (HCMUT-034 and -047, labour LVN-040 and -002), so it is partly task dependent (long prompts), and six of the HCMUT rows ended after 85 to 93 s, the others at 133 to 180 s. Server 82 is shared and GPU 3 was in use by other users at the start of the runs (12.8 GB used before the run). The manifests do not record contention per trial, so the cause is not established | The number of `wall_timeout` rows can differ on a different GPU or load; they are counted as failures, so a run with more timeouts has a lower strict-success bound. Report the count and kinds with the result |
| Re-analysis (Level B) | Deterministic given `trials.jsonl` and the judge attempts (bootstrap seed 20261023) | Identical numbers; only timestamps in generated files differ |
| Reranker GGUF rebuild | Conversion and patching are scripted and the output is hash-pinned | If your file has a different sha256 the preflight refuses it |
| Library versions | Lower-bound requirements only; the GPU packages for scikit-learn, rank-bm25 and scipy are not recorded | Install the versions of section 2.1 for the Mac; for the GPU use the recorded set and report others |

\section{Changes from the Proposal}\label{sec:changes}
\hdr{Scope and users.} The proposal (D1, Application Track) targeted employees and HR staff asking labour-law questions. For D2 we added a second corpus, the academic-affairs regulations of HCMUT used by students and advisers, to test whether the same code serves another domain: wording, tool names and ID rules are per-domain configuration. We claim only what was evaluated: ten HCMUT documents and ten labour-law documents (the 2019 Labour Code with two laws, six decrees and one circular of 2020--2025), snapshot of 22 October 2026, later amendments unchecked. LuatCheck is not legal advice and has not been tried by real users. Intended scenarios: a student looks up a rule and opens the cited section; an HR officer checks a labour-law answer against the cited article; a careless or hostile user pastes a document with injected instructions, and the system must keep its tool boundary and refuse or clarify.

\hdr{Design history.} The first design (v3, controller 2B) was frozen and run first; it reached 12--19\% strict success. An error analysis of its recorded runs found four causes:
\begin{itemize}
\item the controller's own search queries retrieved worse than the question itself (an offline projection puts first-search Recall@3 at 0.71 and 0.62, against 0.95 and 0.98 if the question were the query);
\item it asked for clarification as an exit whenever evidence was missing (37\% and 30\% of answerable tasks without the verifier), although no task expects one;
\item after a verifier rejection it refused in 56\% and 53\% of cases instead of repairing the answer;
\item most rejections were exact-quote mismatches caused by elided quotes.
\end{itemize}
The revision r2 addresses them. The first search is anchored on the question, the clarify and refuse rules are explicit, an answer needs a prior search, and the model's reasoning text is capped. Verifier v2 accepts elided and wrapped quotes, checks numbers in the claim's own sentence and shows the closest source span in its feedback. r2 runs with a 4B controller (chosen) and a 2B controller (lighter option).

\section{Implemented Architecture}\label{sec:arch}
LuatCheck is one agent running a ReAct-style loop~\citep{yao2023react} over retrieval-augmented generation~\citep{lewis2020rag} (Figure~\ref{fig:arch}). Before any model call, input guardrails (regular-expression patterns, shared and per domain; no learned classifier) refuse obviously unsafe input, and the question is wrapped as untrusted text. At each step the controller emits one JSON action: search, read, answer, clarify or refuse. A search ranks records with BM25 and TF-IDF fused by reciprocal rank fusion (RRF), rescores the top 20 with a neural cross-encoder reranker and returns the best five as the observation.

An answer goes through the L1 verifier, which checks in code that each cited record exists and was retrieved, that the quoted sentence appears in it, and that the claim's terms and numbers match the cited text. If the check fails, the verifier's report goes back to the controller for at most two repairs, which is external feedback rather than self-critique~\citep{huang2024selfcorrect}. The loop is bounded to 8 steps, 5 tool calls, 2 repairs and 180\,s. A backend or format failure ends the run as an execution error; it is never turned into an answer or a refusal.

There is one controller and no multi-agent coordination, which keeps permissions and budgets easy to inspect. The chosen system uses the 4B controller; a lighter configuration uses the 2B controller. Both are ternary-quantised models (about 2.1 bits per weight) served by the same llama.cpp server. Everything in Figure~\ref{fig:arch} except the dashed boxes runs end to end; the two orange components, the reranker and the verifier, have on/off switches and are ablated in Section~\ref{sec:eval}. The dashed boxes are implemented but outside every D2 measurement. There is no code-execution tool and no external sender.

\section{Memory and Knowledge Sources}\label{sec:memory}
\hdr{Short-term context.} Each run keeps one message list: the domain system prompt, the question (and any pasted document) wrapped as untrusted input, then alternating action and observation turns. Observations are compacted: a search returns the best-matching clauses of each record with a truncation flag, a repeated query or read returns a short notice, and budget notices tell the model when to answer or refuse. The controller has an 8,192-token context window. The case ledger records queries, retrieved ids, repairs, token counts and times.

\hdr{Long-term memory (implemented, not exercised in D2).} Verified answers can be stored in a local database after the verification gate. Reuse requires a matching index version and a question similarity of at least 0.85, and the reused answer is re-verified. Memory is off in every D2 run and in the demo, so trials stay independent; matching sees only the question and not the facts that decide a case. A fixed set of patterns screens for personal data before a write.

\hdr{Knowledge sources.} Both corpora were built from public PDFs by text extraction, Unicode normalisation and segmentation at section headings. Each record carries its source URL, file hash and page numbers, and the retrieval unit is a record (an article or a clause). The HCMUT corpus has 10 documents and 143 records; five documents are amendment-only and the image-only base regulations are absent, and printed decision numbers come from a web listing. The labour corpus has 10 documents and 458 records; Decree 145/2020 and unnumbered annexes are absent, texts are as promulgated and later amendments are unchecked. Neither corpus has been checked by a domain expert: \pending{university or legal reviewer, if any}.

\hdr{Retrieval and reranking.} The index is built in memory at start-up. BM25 over title and content and TF-IDF over word 1--3-grams are fused by RRF. The top 20 candidates are rescored by a cross-encoder reranker (AITeamVN Vietnamese reranker); records longer than one window are split into overlapping windows of about 1,500 characters and the record keeps its best window. The first search of a run always uses the user's question together with the model's query. Dense embedding retrieval with a persisted vector index is implemented but not evaluated in D2; it is a planned ablation. The reranker runs as a GGUF export on the Mac and as torch fp16 on the GPU server. In a parity probe on 100 benchmark questions, the Mac runtime had a mean per-question Spearman correlation of 0.9994 with the fp32 reference and the same top-1 record in 99 of 100 questions (0.9943 and 100 of 100 for the GPU runtime), so accuracy (GPU) and latency (Mac) describe the same ranking behaviour; we still report them separately.

\section{Evaluation Set and First Results}\label{sec:eval}
\hdr{Benchmarks.} Each benchmark has 50 Vietnamese tasks over its own corpus: 40 single-record, 5 two-record and 5 out-of-scope tasks that must be refused. A task has gold record ids, a short reference answer and verbatim evidence quotes; both files are frozen with hash locks before collection. The tasks were drafted by an AI model, cross-checked by two independent AI verifiers and an AI adjudicator, and mechanical checks confirmed that every quote is verbatim; then group member Võ Phạm Tuấn Dũng reviewed all 100 tasks on 23 October and requested no change. They are AI-written questions over real documents, not real users' questions. A quality audit found no wrong gold answer and three limits:
\begin{itemize}
\item plain BM25 on the raw question already ranks a gold record first for 89\% (HCMUT) and 78\% (labour) of questions, so retrieval cannot separate the configurations;
\item about one third of the answerable tasks can be answered without the corpus (LLM estimate);
\item 22 HCMUT questions pin a document by a decision number taken from a web listing.
\end{itemize}

\hdr{How success is decided.} \emph{Strict success} counts a trial only if the run completed, the behaviour was appropriate (answer when the corpus answers, refuse when it does not), the answer is judged correct and complete, and every factual claim is supported by the sources. Execution errors and failed judgments count as failures, so the rate is a lower bound over all planned trials. It is an LLM estimate, not a human label. Judge-free measures are behaviour match, over-refusal and unsafe answers; Recall@5 of gold records in the agent's trace and citation F1 are lexical, source-id proxies and say nothing about answer correctness. Intervals are 95\% bootstrap intervals over tasks, with the three seeds averaged per task; with 50 tasks, differences below about 10 percentage points are not detectable. Definitions are in the repository (benchmark and metrics reference).

\hdr{LLM judge and its check.} An LLM judge (DeepSeek V4.1 Flash, through an API gateway) rates each output blind to the configuration and the verifier outcome; it is used offline only, and the model revision behind the route is not pinned~\citep{deepseek2026api}. LLM judges can be biased~\citep{zheng2023judge}, so the group labels a stratified blind sample of about 30 items per benchmark, taken from the outputs of the chosen 4B system, and computes agreement and Cohen's $\kappa$ against the judge. \pending{Human audit not yet done: agreement and $\kappa$ unavailable.} Until then every success figure is an estimate. Separating answer correctness from citation support follows~\citet{gao2023alce}.

\hdr{Design.} The chosen system, \emph{L1+rerank}, is compared with two simpler configurations: \emph{OFF} (no verifier, no reranker) and \emph{L1} (verifier with repair, no reranker). Each runs three seeds on 50 tasks per benchmark. Two diagnostic baselines (one seed, not system variants) bracket the results: \emph{closed-book} (the question only, no tools or documents) and \emph{oracle} (the gold records given up front, answerable tasks only). A run of one controller thus has 900 system trials plus 190 baseline trials, 1{,}090 in all, every one recorded. The first design (v3, 2B) and the revised design with the 2B controller (r2-2B) were run the same way. Accuracy was collected on a shared server GPU (one NVIDIA H100); latency is measured separately on an Apple M4 laptop (16\,GiB), one query at a time.

\hdr{What the numbers say.}\par\noindent\textbf{(1) Model size and revision both matter, and the model matters more} (Figure~\ref{fig:bars}). For the chosen configuration, strict success is 60.7\% [50--71] on HCMUT and 56.7\% [47--67] on labour with the 4B controller, against 28.7\% and 28.0\% with the 2B controller and 14.0\% and 18.7\% for the first design. Swapping the controller, 2B to 4B, adds 32.0 points [21.3, 42.0] and 28.7 [18.0, 39.3]; the revision alone, v3 to r2 at 2B, adds 14.7 [6.0, 23.3] and 9.3 [0.7, 18.0] (paired differences, 95\% intervals; all twelve paired differences across the three configurations exclude zero; full tables in the appendix).

\par\noindent\textbf{(2) The verifier and the reranker did not raise strict success.} In Table~\ref{tab:main}, OFF is highest (70.0\% and 62.0\%). L1 changes strict success against OFF by $-6.0$ [$-16.0$, $+4.0$] and $-9.3$ [$-18.7$, $0.0$] points, and the reranker against L1 by $-3.3$ [$-13.3$, $+6.7$] and $+4.0$ [$-6.0$, $+14.0$]. Table~\ref{tab:diag} shows why: both make the system refuse more, because an answer the verifier rejects twice ends as a refusal (10 to 18 of 150 trials per configuration, always on tasks where an answer was expected). Unsafe answers on the 15 out-of-scope trials per row do not fall consistently, from a very small base, and Recall@5 is already 0.98--0.99 without the reranker. The chosen system keeps both components for the guarantee of a checkable citation; D3 tests on a harder held-out benchmark whether the cost in refusals is justified.

\par\noindent\textbf{(3) Baselines.} Without documents the 4B model scores 2.0\% [0--6] on HCMUT and 24.0\% [12--36] on labour, so part of the labour score can come from the model's own knowledge. With the gold records in front of it, the oracle reaches 82.2\% [71--93] and 75.6\% [62--87] on the answerable tasks: even with perfect evidence the 4B controller misses strict success on about one task in five, against 69.6\% and 60.7\% for the agent without verifier on the same tasks. 17 of 1,090 trials ended as execution errors (wall-time limit); they count as failures.

\hdr{How to read the gain.} The first design was frozen and run before any change. The revision r2 was designed after we had read the v3 results and their failure analysis on the same 100 tasks, so its gains are optimistic: they show that the diagnosed problems were real and fixable, not how the system will perform on unseen questions. D3 confirms them on a new held-out benchmark. Other limits: success is an unaudited LLM estimate; the benchmarks are AI-written, easy for retrieval, and partly answerable without documents; three seeds add no tasks, so intervals are over 50 tasks.

\hdr{Cost and latency.} The controller and reranker run locally, so there is no per-call API cost. For the chosen system the controller reads on average 12,070 (HCMUT) and 11,477 (labour) tokens and writes 763 and 865 tokens per trial, over 3.4 and 3.7 model calls. The judge cost, as reported by the gateway and not an invoice, was USD 1.06 and USD 1.10 for the two 545-trial runs. Collecting a run took 34 and 33 minutes of wall time on the shared H100 (GPU-active hours were not measured). Latency on the laptop for the chosen system with the 4B and the 2B controller: \pending{Mac M4 trial latency (p50 and p95) and peak memory; runs in progress}.

\section{Threat Model}\label{sec:threat}
\hdr{Assets.} (A1) Faithfulness: answers and citations that users rely on must trace to source sections~\citep{magesh2025hallucination}. (A2) User data: questions, pasted documents, memory and the audit log. (A3) Integrity of corpora, domain profiles, prompts, model weights and the frozen benchmark. (A4) The tool boundary: no unreviewed write or egress. (A5) Availability of a bounded local machine.

\hdr{Attacker.} The attacker can submit arbitrary questions and pasted documents through the interface or API (instruction override, delimiter spoofing, prompt or memory exfiltration, requests to evade a regulation), including text copied from a hostile third party. The attacker cannot change code, corpora, configuration, weights, the ledger or the approval state of the trusted UI, and cannot reach loopback servers or other users' sessions. Non-goals: a compromised host or supply chain, poisoned official sources, multi-tenant isolation, and the correctness of the regulations themselves.
